| ④ | 分类提速 | `spots.Board.scores` 顺手记下**多格模板逐位置最优**，`objects()` 直接复用（原来把多格像素匹配**整个重算一遍**） | 缓存路径 vs 强制重算**逐格一致**（3 帧）；1.5~2.2× | 分类少一次重复匹配 |
| ⑤ | 截图去重 | `Bot.snap` 按帧戳去重（帧没变不付 PNG 编码 150~300ms + 解码）；`save=True` 绕过 | 同帧第二次不抓帧；换帧立刻失效 | 每轮多次 snap 时明显 |
| ⑥ | sleep 条件化 | `enter_map` 加载轮询 `sleep(1.5)`→`wait_stable(1.2)`；外层 `1.5`→`0.3`；`_board_dimmed` 复查 `sleep(2.0)`→`wait_stable(2.0)` 兜底 | 上限不变（仍 2s/9 轮），只是"一停就走" | 进图那 ~27s 砍成 ~10s |
| ⑦ | 同帧并发 | `classify_async_start/join`：轮首把分类丢后台线程、与 Java OCR 重叠 | 并发结果与串行**逐格一致**（35 格） | **默认关**，见 §3 |

### ①为什么能这么砍（实测，不是猜）
真机参考帧上量出来的两条硬事实：
- 标记的**最佳尺度只落在 3.8 / 4.1 / 4.4**（其余 12 档从来没赢过）；
- 标记模板中心相对**格心恒为 (-36,-36)**（两帧逐像素一致）⇒ 它不是"乱落在格心附近"，
  而是**格子美术里的固定位置**。
⇒ 105 次全图匹配 = 大量纯浪费；定点窗口把匹配面积降到约 1/100。

## 2. 安全边界（没真机可验时的底线）

- 旧 `scan_board` / `probe_top` **一字未动**，保留作对拍基准（门禁里真跑两版逐格比）。
- `fixed_ref` 只做"快查"，调用方一律**回退**原多尺度路 ⇒ 模板没裁好也不会把面板认没。
- `objects()` 复用缓存时有「**同一张 img 对象**」守卫 ⇒ 换帧绝不复用旧值。
- OCR/截图缓存只在**帧戳相同**时命中 ⇒ 像素逐字节相同才复用，语义上不可能串味。
- ⑦ 默认关；开了也有「上一轮没跑完就不再提交」的防排队逻辑。

## 3. 留给真机的部分（我没法验，如实列出）

| 项 | 为什么留 | 真机怎么定 |
|---|---|---|
| **⑦ 同帧并发开不开** | 手机核数不够时两边抢 CPU，净收益只能实测 | 跑一局 `MAPBOT_PARALLEL=1`，比同一张图的「耗时分布」；没变快就保持默认关 |
| **⑤ 传输瘦身**（JPEG / ARGB 直传） | 要动 Java ⇒ 出整包；方案本身还依赖"Chaquopy 传 8MB 的开销"实测 | 先量 `grabRefPng` 的占比（看「截图 Xs」），占比 <8% 就不值得动 |
| **② 面板/战斗按钮模板** | 定点层已就绪，但**面板按钮模板必须从真机帧裁**（我没有那批帧） | 真机上停在对应界面抓一帧 → 裁进 `templates/ui/` → `fixed_ref.find` 立即可用 |
| **④ 真正的"每轮增量分类"** | 需要"失效集"的口径（连锁揭示范围不好预判）；口径错了会**静默丢目标**（白烧体力） | 用「耗时分布」看分类是否仍是瓶颈；是的话再按 tap 位置做失效集，并配真机对拍 |

## 4. 真机验收清单（开机后照着看）

1. **最重要**：悬浮条那份「⏱ 耗时分布」里，**`棋盘识别` 与总时长都应明显下降**；

4. **进图与开打**：进图不再有"点完呆等"的长停顿；开打判定仍然正常（不会点完战斗就走）。
5. **停止键**：点 ■ 仍应立刻停（`wait_stable` 每轮都查停止位，语义未变）。

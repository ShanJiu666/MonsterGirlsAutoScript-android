## ① 重写 `marks.scan_board` —— 10s → <0.5s/次，**每轮省 5~10s**

**文件**：`app/src/main/python/marks.py`（全改在这一个文件）
**根因**：`scan_board` 每次 `7 个模板 × 15 个尺度 = 105 次`，每次都拿 **1080×740 整条棋盘带**
跑带掩码 `TM_SQDIFF`；但标记按设计**只可能出现在格心 ±65px**（`MARK_BOX_REF=65`，GRID 常量）。

**做法（三个砍法叠加，全在参考系，全分辨率零特例）**：
1. **搜区**：整条带 → **35 个格心小块**（130×130，格心 = `cell_center(r,c)`，GRID 常量）。
   实测单次 0.089s → 0.007s。
2. **尺度**：`GLYPH_SCALES` 15 档 → **按格距 px 直接算 2~3 档**（px=144 时尺度 ≈4.5，
   随分辨率线性 ⇒ 不用扫 15 档）。`probe_top` 仍可用全档做诊断（它只在 marks:none 时跑）。
3. **形状分走灰度**（实测 3.0×），颜色判别本来就有 `color_score` 兜底。
   ⚠ 灰度会改形状分分布 ⇒ **SHAPE_MIN/COLOR_MIN/TYPE_MIN 必须重新标定 + 真机复验**（规矩 4）。

**附带（零风险，顺手做）**：
- `load_tpls()` 现在**每次调用都重新读盘解码**（实测 2.4ms/次）⇒ 加模块级缓存。
- `mapsim.py:817` 是另一个 `scan_board` 调用点（离线建盘用），同步受益，不用改它。

**验收**：
- 离线：`_verify/phone_redmi_grassland/board_grassland_r0.png` 等 4 张真机帧，
  新旧输出逐格一致（sid/marks/位置 ±5px）。
- **先把新实现写成 `scan_board_fast`，旧 `scan_board` 保留**，门禁里并存对拍一致后再切换
  （防止「看着像就直接换」；没有真机，这一步就是等价性证据，别省）。
- 阈值标定：用 `_verify/` 里带标记的真机帧 + 不带标记的负样本帧，扫阈值网格，
  定「不误报（负样本 0 命中）不漏报（正样本全中）」的新阈值；标定过程写进门禁。

## ② 参考系定点层 `fixed_ref.py` + **OCR 按帧戳缓存** —— 每图省 30~50s

> 手机端版 `fixed.py`。关键洞察：所有设备帧都被 RefMapper 归一到 1080×1920 参考系 ⇒
> **参考系里的一套锚点/模板，天然全分辨率生效**（PC 锁死 720p 反而做不到）。

**新文件**：`app/src/main/python/fixed_ref.py`（纯 Python，热更可发）
**做法**：
1. **定点模板**替掉这些 OCR（坐标全在 `layout.REF`/`fixed.py` 已有）：
   结算三键（`bottom_close/settle_replay/settle_skip`）、战斗/探索按钮、背包 X（`close_bag`）、
   底部导航 5 键、「进入地图」(`enter_map`)、「结束冒险」(`end_adv`)。
   - 模板从**真机参考系帧**裁（`_verify/` 里有 1080×1920 帧；存 `assets/mapbot_pack/templates/ui/`）。
   - 存在性判断用 `TM_CCOEFF_NORMED`（参考 `mapbot_pc/fixed.py` 的 `find/has`，阈值 ~0.62）。
   - **仍然 OCR**：体力、倒计时、图名、价格、道具名（内容会变）。
2. **OCR 按帧戳缓存**：`DeviceApi.frameStamp()` 已有。在 `mapbot.Bot.ocr()` 里加：
   `frameStamp` 相同 + 相同 `band/min_conf` ⇒ 直接复用上一次结果
   （现在 popups / panel_seen / stamina / slots 常在**同一帧**各扫一遍，每遍 1.5~2s）。
   ⚠ 缓存键要含 band+min_conf；帧戳变了立刻失效。

**验收**：
- 定点模板：正样本命中 / 负样本不命中（学 PC `verify_fastpath.py` 的口径，写进主门禁）。
- OCR 缓存：同一帧两次 `ocr()`，第二次 <5ms；统计里 OCR 次数/秒数显著下降。
- ⚠ 这是「改判据来源」级别的改动 ⇒ 用 `_verify/` 的真机帧离线对拍「认页/认面板」没退化。

## ③ 轮询循环去 OCR —— 每场战斗省 3~8s

**文件**：`explore_loop.py` 的 `start_fight`（:2876）/ `wait_end`（:3298）
**根因**：等战斗开打/等结算 = 每隔 0.6~2.5s **花 1.5s 做一次 OCR 认字看状态变了没**。
**做法**：
1. 用 Java 侧 `waitChange/waitStable`（60~80ms 轮询纯像素，≈0 成本）判「画面停了」；
2. 停了用 ② 的定点模板查「关闭/战斗」在不在；
3. 模板不认才回退 OCR。
⚠ `wait_end` 里大拇指格要**细等**（等奖励行稳定才能判大拇指），这条语义保留，只换「怎么等」。

**验收**：离线门禁（重点：`wait_end`/`start_fight`/`dice` 相关的 v1.22~v1.26 那几组），
确认摇色子触发逻辑、结算关面板逻辑没变。

## ④ 棋盘分类增量更新 —— 每轮省 ~1.5s

**文件**：`spots.py` 的 `Board.state` / `explore_loop.py` 的 `cells_of` 调用处
**根因**：每轮 `Board.state` **全量 35 格**（1.8s/次），但一轮里只有**被点的那格 +
连锁揭开的邻居**会变。
**做法**：
1. 进图首轮全量；之后按 tap 位置算「失效集」（被点格 + 4 邻 + 多格块的成员格），
   只重算受影响格（单格 ~50ms）。
2. 未变格的 score/ratio/雾格剪影直接复用上一轮（`st['obs']` 的跨轮累积机制已存在，顺着做）。
⚠ 连锁揭示的范围不好预判 ⇒ 第一版保守：tap 后只重算「该格 + 上下左右 + 被标记为连锁源的格」，
   其余沿用；发现「该变没变」的 case 再扩失效集。

**验收**：离线 4 帧，增量结果与全量一致；`st['obs']` 累积下「已揭示 N」单调不减、无回退。

## ⑤ 截图去重 + 传输瘦身 —— 每图省 10~15s

**文件**：`mapbot.py`（`Bot.snap`）+ `DeviceApi.java`（新加一个方法，动 Java ⇒ 整包）
**做法**：
1. `Bot.snap` 按 `frameStamp` 去重：帧没变直接复用 `self._img_arr`，
   不付 PNG 编码（150~300ms/次）+ `imdecode`。现在每轮 snap 3~5 次、很多是同一帧。
2. **传输瘦身**（整包）：Java 新增 `grabRefArgb()` 直传 `int[]` 像素（零编码），
   或 `grabRefPng` 改 JPEG(q=80)（编码 ~30~60ms）。OCR 用 `raw.copy()` 本就走 Bitmap 不走 PNG，互不影响。
⚠ JPEG 有损 ⇒ 若选 JPEG 路线，**识别精度要全量门禁 + 真机复验**；选 ARGB 直传则零风险但 Java→Python
   传输量大（1080×1920×4 ≈ 8MB/次），先实测 Chaquopy 传 8MB 的开销再定。

**验收**：统计里「截图 Xs」显著下降；帧没变时 `snap` <10ms。

## ⑦ 感知流水线（压轴，结构性，-15~25%）—— 放最后

**根因**：主循环严格串行：snap → OCR → 分类 → 标记 → 规划 → 点。
**做法**：
1. **同帧并发**：OCR（Java 线程）与 分类+标记（Python）对**同一帧**同时算
   （cv2/ONNX 都是 native 调用，GIL 大部分放开）。
2. **预取**：战斗动画等待期间预取下一帧、预跑分类。
⚠ 改动面最大、回归风险最高 ⇒ **必须在 ①~⑥ 全部落袋、且确认感知仍是瓶颈之后再做**。
   先做 1（同帧并发），2（预取）看情况。
